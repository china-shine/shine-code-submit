## 零、新手快速入门(先读这个)

刚接触这个项目?花 3 分钟搞懂下面几个概念,后面的数据就都好懂了。

### 这个平台是干嘛的?

**AI 效能平台**(tokenserver)是一个**报表看板**,统计一个团队用 **Claude Code**(Anthropic 的 AI 编程助手)的情况:谁在用、用了多少、写了多少代码、花了多长时间。目的是让团队/管理者了解 AI 编程的使用情况,不涉及代码内容,只统计用量数字。

### 3 个必须先懂的概念

#### ① 会话(session)—— 一次连续的 AI 对话

你打开 Claude Code 开始跟它聊(写代码、问问题),到结束算一个「会话」。一个会话里可能有很多轮来回(你问一句、它答一句)。页面上「对话次数」统计的就是会话数。

#### ② Token —— AI 处理的文字量(「字数流量」)

AI 不按「次」或「小时」计费,而是按处理的文字量(token)收费。**1 个 token 大约 = 0.75 个英文单词、或不到 1 个汉字**。一段对话 token 越多,说明内容越长/越复杂、花钱越多。

token 分四种:

| 字段 | 通俗理解 | 计费(相对输入的倍数) |
|---|---|---|
| **输入** (input) | 你发给 AI 的内容(问题 + 历史上下文) | 1×(基准) |
| **输出** (output) | AI 回给你的内容 | **最贵**(约 3~5×) |
| **缓存写入** (cacheCreation) | 把重复内容存起来,下次不用重算(第一次存) | ~1.25×(稍贵) |
| **缓存读取** (cacheRead) | 复用之前存好的内容(命中缓存) | **~0.1×(便宜 90%)** |

> 为什么要分这四种?因为 Anthropic 的计费规则不同——光看一个总数不够,要看构成。页面上「总 Token」= 这四个加起来。

#### ③ 活跃时长(activeMs)—— 跟 AI 交互的时长(估算值)

平台会估算你「跟 AI 互动了多久」。**注意这不是真实工时**——它看不见你离开 AI 自己写代码、查资料的时间。详见「通用口径 3」。

### 数据怎么来的?(你不用做任何操作)

```text
你在电脑上用 Claude Code 写代码
      ↓  (Claude Code 自动把每次对话明细记录到本地文件)
后台小程序(daemon)读取这些记录,统计 token / 时长 / 代码行
      ↓  (默认每 10 分钟自动上报一次,可在设置里改 reportIntervalMin)
AI 效能平台 收数据、存库、画成图表
      ↓
你在浏览器里看到的这个 dashboard
```

只要团队装了 shine-worklog,数据全自动采集上报,**不需要手动填报**。

## 一、数据从哪来

```text
Claude Code transcript(.jsonl)
   │  shine-worklog daemon 扫描(逐行解析/校验/去重,口径对齐 ccusage)
   ▼
daemon 定时上报(默认 10 分钟)→ POST /api/report(gzip + 增量水位)
   │  tokenserver saveReport 落库
   ▼
tokenserver SQLite:sessions / projects / git_changes / worklogs 四表
   │  前端请求时二次聚合
   ▼
Dashboard(/api/stats · /api/sessions · /api/member · /api/denominator-breakdown · /api/member/:X/worklog)
```

### 上报机制(daemon → tokenserver)

| 机制 | 说明 |
|---|---|
| **上报身份** | `git config user.name`(读全局配置,一台机器所有项目都归该用户名下)。采集不到时**跳过本次上报**,不以「未知用户」上传。多台机器同名在平台上合并累积。 |
| **gzip 压缩** | POST 带 `content-encoding: gzip`,tokenserver 按 header 解压(兼容不压缩的老上报)。 |
| **增量水位** | `settings.json` 持久化 `lastReportAt`,每次只发 `last_activity >= 水位` 的 session;成功推进,失败不推进(下次重发不丢);重启不重置。 |
| **24h 全量校准** | 每满 24h(或 daemon 升级后)强制 `since=0` 全量重报;`git_changes` 按 hash 幂等 upsert,重报不重计。 |
| **禅道工时全量** | worklogs 忽略增量水位,每次全量上报(daemon 读 `submitted/<date>.jsonl` 提交流水)。 |

### tokenserver 四张表

#### sessions 表(每行 = 一个会话)

| 字段 | 说明 |
|---|---|
| `sessionId` | **主键** |
| `gitUser` | 上报身份(user.name) |
| `cwd` | 项目路径 |
| `lastActive` | 最后活跃(毫秒时间戳) |
| `input` / `output` / `cacheCreation` / `cacheRead` | Token 四字段 |
| `added` / `deleted` / `modified` | 代码行三字段;**可为 NULL** = 无数据(daemon 侧 events 7 天滚动修剪后的老会话),落库时保留旧值不覆盖(COALESCE,NULL≠0 行) |
| `activeMs` | 活跃时长(估算) |
| `title` / `updatedAt` | 标题 / 更新时间 |

#### projects 表(每行 = 一个用户 × 项目)

| 字段 | 说明 |
|---|---|
| `(gitUser, cwd)` | **复合主键** |
| `name` | 项目名 |
| `gitRemote` | 远程仓库 URL |
| `lastActive` / `updatedAt` | 最后活跃 / 更新时间 |
| `version` | 该成员最新上报的 daemon 版本(成员列表「上报版本」列) |

#### git_changes 表(每行 = 一个 git commit)

| 字段 | 说明 |
|---|---|
| `hash` | **主键**(commit SHA,幂等去重) |
| `gitUser` / `cwd` / `ts` | 谁 / 哪个项目 / 何时提交 |
| `added` / `deleted` | 该 commit 代码变化行 |
| `aiAdded` / `aiDeleted` | 其中行级匹配命中 AI 操作的行数 |

> 来自 daemon 上报的 `ReportProject.gitCommits`,`hash` 相同的全量重扫不重计(取 MAX)。是「AI 代码占比」的分母/分子来源。

#### worklogs 表(每行 = 一条禅道工时提交记录)

| 字段 | 说明 |
|---|---|
| `(gitUser, date, sessionId, taskId, subId)` | **复合主键**(taskId 空兜底 0;`subId` = 提交流水号 `<date>:<行号>`) |
| `repo` / `branch` / `start` / `end` / `minutes` / `hours` | 会话信息与工时 |
| `taskName` / `projectId` / `projectName` / `work` / `status` / `zentaoUrl` | 任务信息与提交文案 |
| `cwd` / `updatedAt` | 项目路径 / 更新时间 |

> 来自 daemon 每次上报全量读 `submitted/*.jsonl` 提交流水(忽略增量水位)。是成员详情「禅道工时」表的数据源。

#### 去重(幂等)规则

| 表 | 规则 |
|---|---|
| sessions | 同 `sessionId` 重复上报时,仅当新数据 `lastActive ≥ 旧` 或 `cwd` 变了才覆盖 |
| git_changes | 按 `hash` 幂等(相同 commit 不重计) |
| worklogs | 按复合主键 upsert 累积(跨项目/跨天长期保留) |

### 聚合/分页接口

| 接口 | 作用 | 后端函数 |
|---|---|---|
| `GET /api/stats` | 总览全部聚合 + 成员列表 | `getStats` |
| `GET /api/sessions` | 会话明细分页(总览表 / 成员详情表) | `getSessions` |
| `GET /api/member/:gitUser` | 单成员 KPI + 趋势 | `getMember` |
| `GET /api/denominator-breakdown` | AI 占比分母构成弹窗 | `getDenominatorBreakdown` |
| `GET /api/member/:gitUser/worklog` | 成员禅道工时分页 | `getMemberWorklogs` |

## 二、通用口径(先读这节)

### 1. Token 四字段 与 rawTotal

每个会话有四个 token 字段(来自 transcript `message.usage`,口径与 [ccusage](https://github.com/ccusage/ccusage) 一致):

| 字段 | 含义 |
|---|---|
| `input` | 输入 token |
| `output` | 输出 token |
| `cacheCreation` | 缓存写入(prompt caching 创建) |
| `cacheRead` | 缓存读取 |

- **rawTotal** = input + output + cacheCreation + cacheRead(四字段全量)。**凡页面上写「总 Token」的,都是 rawTotal**。
- **cache** = cacheCreation + cacheRead(趋势图「缓存」视图、饼图「缓存 Token」、成员详情构成行)。
- **inoutTokens** = input + output(**不含缓存**)—— 只用作「Token 效率(行/M)」的分母(见口径 11)。

#### 缓存两字段详解(prompt caching)

先理解一个前提:**大模型 API 没有记忆**,每次请求都是独立的——必须把完整上下文(系统提示 + 工具定义 + 全部历史对话)每轮重新发一遍,且聊得越久单轮越大(长会话单轮可达几十万 token)。第 N 轮发的内容,开头绝大部分与第 N-1 轮完全相同。

prompt caching 解决的就是这个重复计算:服务端把**已算过的前缀**存起来复用:

| 阶段 | 发生什么 | 记入字段 | 价格 |
|---|---|---|---|
| 新前缀第一次计算 | 算一遍 + 存入缓存 | `cacheCreation` | ~1.25× |
| 后续请求前缀命中 | 不重算,直接复用缓存 | `cacheRead` | **~0.1×** |

缓存有存活期(约 5 分钟,每次命中会续期),间隔太久未命中则重新写入。

**怎么读缓存数字**:

- 长会话(几百轮)里,同一份上下文被重发几千次且几乎全部命中 → **cacheRead 可占 rawTotal 的 96%+**,这是长会话 + 缓存生效的正常形态;
- **缓存大 ≠ 花钱多**:cacheRead 按 0.1× 计费,占比高恰恰说明「省钱机制正在生效」;
- **Token 效率分母剔除缓存**:缓存读是廉价复用,不是真实消耗;把它算进分母会把效率稀释到失真(实测:含缓存 10 行/M,不含 237 行/M);
- 验算提示:看到总 Token 很大、效率却不高时,先看构成里缓存占比。

### 2. 代码行 lines

`added`(新增)/ `deleted`(删除)/ `modified`(修改)三字段,来自 daemon 上报。**超过 daemon events 保留窗口(7 天)的老会话上报 NULL**(无数据≠零行)——落库用 COALESCE 保留平台旧值,防 24h 全量校准把历史行数清零(2026-08-17 起)。

- **lineTotal** = added + deleted + modified。凡「代码变动行数」都是三者之和。
- 会话表「代码变动」列**分别**显示 `+added -deleted Mmodified`,不合并。

### 3. 对话时长 activeMs

> **估算值,不是真实工时** —— 度量「与 Claude 交互的活跃度」。

**gap-aware 切 burst 算法**:把会话内所有交互(usage 消息)时间戳升序排列,相邻间隔 **≤ 1 小时**的归同一段 burst,**> 1 小时则截断**(视为用户离开)。每段 burst 时长 = `(首条→末条跨度) + 10 分钟 buffer`(补读回复/思考/测试),多段求和。

| 时间戳 | 算法 | 结果 |
|---|---|---|
| `[10:00, 10:05, 10:12]`(间隔都 <1h) | 跨度 12min + 10min buffer | **22min** |
| `[09:00]`(单条,单点 burst) | 0 + 10min buffer | **10min**(下限) |
| `[09:00, 12:00]`(间隔 3h,断两段) | (10min) + (10min) | **20min**(中间 3h 不计) |

**关键性质**:

- 相邻交互间隔 **≤ 1h 计入**、**> 1h 截断不算**。
- 每段 burst 末尾无条件 +10min → `activeMs` **下限 10min**(一句 30 秒问答也算 10min)。
- **自己写代码/查资料只要 < 1h 回到 Claude,这段时间会被算进去**;只有离开 ≥ 1h 才丢弃 → **不是真实工时**,「适合看交互密度,不适合当人工工时报出去」。

### 4. 日期范围(闭区间,按 lastActive)

前端传 `start` / `end`(YYYY-MM-DD),后端 `parseDateRange`:

- **from** = 开始日 `00:00:00.000`(本地时区);留空 = `0`(不限起始)。
- **to** = 结束日 `23:59:59.999`(次日 0 点 − 1ms);留空 = `MAX_SAFE_INTEGER`(不限结束)。
- 过滤条件 `WHERE lastActive >= from AND lastActive <= to`,**闭区间**,会话按**最后活跃时间**归属;git_changes 按commit 时间 `ts` 过滤(AI 占比的日期口径 = 提交日)。
- **首次打开默认最近 30 天**;点「重置」回到全量范围。

### 5. 趋势聚合粒度(按「日」)

趋势图与 KPI 卡 sparkline 均按**日历日**聚合(标签 `MM-DD`)。后端另支持 `week` / `month`,当前 UI 固定 `day`。

### 6. 成员 / 项目过滤

- **成员筛选**:URL `members=用户A,用户B` → SQL `gitUser IN (...)`,影响聚合数据和会话表。
- **`allMembers`**(下拉选项)= 全表 `SELECT DISTINCT gitUser`,**不受任何过滤影响**。
- **`activeMin/activeMax`** = 当前过滤后数据的 lastActive 范围(顶部「范围徽章」用)。
- **`dataMin/dataMax`** = 全表(无过滤)范围(「重置」按钮用)。

### 7. 「真项目」判定

项目榜、活跃项目数只统计「真项目」,排除盘根/家目录/桌面等:

| 情况 | 判定 |
|---|---|
| 空 / 段数 ≤ 1(如 `C:`) | 否 非真项目 |
| 段数 3 且第 2 段 = `users` | 否 家目录 |
| 段数 4 且 = `users/.../{desktop,documents,downloads}` | 否 桌面/文档/下载 |
| 其他 | 是 真项目 |

> Token 总量、对话次数、代码行、成员榜等**不依赖**真项目判定,用全部会话。

### 8. 0-token 会话的口径差异(务必注意)

有些会话四字段 token 全为 0(如纯读取、出错)。它们在不同地方口径不同:

| 是否计入 0-token 会话 | 涉及数据 |
|---|---|
| **计入**(不过滤) | KPI「对话次数」、KPI「活跃项目」、对话时长、代码行、总 Token、趋势、饼图、成员榜、项目榜 |
| **不计入**(过滤 `token>0`) | 会话规模分布、最近会话表(总览/成员详情)的 `total` 与列表行 |

**因此**:KPI「对话次数」≥ 最近会话表总条数(当存在 0-token 会话时)。**正常,不是 bug**。

### 9. AI 代码占比(只统计有 transcript 覆盖的 commit)

「AI 代码占比」= AI 代码行 / 代码变化行,**仅统计有 transcript 覆盖的 commit**(`aiAdded > 0 || aiDeleted > 0`,纯删除型 AI commit 也计入):

```text
AI 代码占比 = Σ(aiAdded + aiDeleted) / Σ(added + deleted)
(cap 100%,分母 0 → N/A)
```

| | 口径 | 关键特性 |
|---|---|---|
| **分母** | 该范围所有有覆盖 commit 的 `added + deleted` 之和 | git 净变化,反复编辑被折叠;包括 AI 没碰过的行 |
| **分子** | 其中能行级匹配上 AI 操作的行(`aiAdded` / `aiDeleted`) | **分子 ⊆ 分母**;AI 删除的行(重构删旧代码)同样计入 |

**怎么判定一行是「AI 写的」—— 认行不认 commit,四条规则**:

1. **只认 4 个编辑工具**:Edit / Write / MultiEdit / NotebookEdit;Bash/Grep/Read 等不算(`npm install` / `create-vite` / build 产物不计入分子);
2. **逐字精确匹配**:commit 行内容(连缩进)去 AI 操作行集合 `set.has()` 查,**宁漏不错**——被格式化改过一个空格就不匹配;
3. **累积匹配**:AI 操作行集合跨会话累积,手动 commit 的 AI 代码也能识别(不靠 `Co-Authored-By` trailer);
4. **认行不认 commit**:不看 commit 作者和 message,只看行的内容来源。

**分母里注定不含分子的部分**(占比低于直觉的正常来源):`package-lock.json` 等安装产物、脚手架模板、构建产物、格式化输出——计入分母但 AI 没「逐行写过」。

> 实测(2026-08-14 patientMsgService 初始提交):全部分母占比 42%,剔除 package-lock 后 82.8%,再剔除脚手架后 **98.6%**。

- **无覆盖的 commit(`aiAdded = 0 且 aiDeleted = 0`)不计入分母**——无法判定,计入只会稀释拉低数字。
- **可选 host 白名单**:配置文件 `aiStatsHosts`(数组),配置后只统计命中指定 host 的 commit。空/不配 = 不过滤。

### 10. 两套「代码行」口径:会话行(过程量)vs commit 行(结果量)

页面上有**两个都叫「代码行」的数字,口径完全不同**,不要互相印证:

| | 「代码变动行数」(KPI / 成员列表 / 会话表) | 「AI 代码占比」的分母 |
|---|---|---|
| **数据源** | AI 工具操作(Edit/Write)的 diff,**不依赖 git** | `git log -p`(已提交),**必须 commit 才有** |
| **算什么** | 每次操作 +/- 行**全部累积**(中间版本反复计) | commit 的净变化(反复编辑被折叠) |
| **语义** | 「AI 这场对话动了多少次代码」(过程量,偏大) | 「最终提交改了多少」(结果量,偏小) |

> 实测(2026-08-13 livesetting):会话行 **2280** vs commit 分母 **684**,差 3.3 倍——正常,不是 bug。

**推论**:不 commit 的日子里,Token 效率照常出数,AI 代码占比显示 N/A——两者不同空属正常。

### 11. Token 效率(行/M)

```text
Token 效率 = 代码变动行数 / ((input + output) / 1,000,000)
```

| | 口径 | 关键特性 |
|---|---|---|
| **分子** | 会话代码变动行 `Σ(added+deleted+modified)`,中间版本全部累积 | 过程量,不是 LOC,不是 commit 净变化 |
| **分母** | inoutTokens = `input + output`,**不含缓存** | 缓存读是廉价复用不算真实消耗;分母 0 → 显示 0 |

**怎么读这个数**:

- 数值高 = 单位 token 产出多(批量生成/新建文件型天然高);
- **数值低 ≠ 效率退步**:分析/读源码/改文档型工作 token 重、变动行少,天然偏低;
- 跨成员对比时注意工作类型差异,写业务代码的和做调研分析的没有可比性。

## 三、总览页

### 3.0 页面顶部状态

- **标题**:「数据总览」/「成员分析」(按所在页)。
- **状态行**:`{活跃成员} 成员 · {会话数} 会话 · 更新于 {刷新时刻}`。
- **页面不自动轮询**:数据变更需手动点「刷新」;新数据本身还依赖 daemon 定时上报(默认 10 分钟)。
- **范围徽章**:`{activeMin} — {activeMax}`,当前过滤后数据的**实际活跃时间范围**(不一定等于你选的日期范围)。

### 3.1 KPI 卡(7 张)

数据来自 `stats.totals` + `stats.daily`(sparkline 用)。

| KPI | 含义 | 计算规则 |
|---|---|---|
| **总 Token 消耗** | 范围内所有会话的原始 token 总量 | `Σ(input+output+cacheCreation+cacheRead)`;副标拆「输入 / 输出」 |
| **对话次数** | 会话条数 | `Σ 会话行数`(含 0-token);sparkline 按日会话数 |
| **对话总时长** | 各会话 gap-aware 活跃时长之和 | `Σ activeMs`;副标「gap-aware 估算 · 1h 间隙截断」 |
| **代码变动行数** | added+deleted+modified 之和 | `Σ(added+deleted+modified)`;副标 `+added -deleted Mmodified` |
| **活跃成员** | 范围内出现过的 gitUser 去重数 | `memberAcc.size` |
| **活跃项目** | 范围内「真项目」数(跨用户) | `realProjKeys.size`,key = `gitUser\0cwd` |
| **AI 代码占比** | AI 行 / commit 变化行(**估算**) | `min(100%, AI行/总行)`;副标「AI X / 共 Y 行」;分母 0 → N/A;「分母」按钮开弹窗(见 3.8) |

### 3.2 Token 消耗趋势图

数据 `stats.trend`(按日分桶)。4 个视图切换:

| 视图 | 计算 |
|---|---|
| **总量** | `input + output + cacheCreation + cacheRead` |
| **输入** | `input` |
| **输出** | `output` |
| **缓存** | `cacheCreation + cacheRead` |

### 3.3 Token 构成饼图

数据 `stats.composition = { input, output, cache }`,中心总数 = 三段之和(= rawTotal)。

| 段 | 计算 |
|---|---|
| 输入 Token | `Σ input` |
| 输出 Token | `Σ output` |
| 缓存 Token | `Σ(cacheCreation + cacheRead)` |

> 三段同除一个分母,精确值加总 = 100%;各自舍入后可能 99.9%/100.1%。实测算例:输入 124.7M ≈ 3.3%、输出 29.5M ≈ 0.8%、缓存 3.66G ≈ 95.9%。

### 3.4 Token 消耗排行(成员 / 项目 两 tab)

**成员榜**:按该成员全部会话 rawTotal 降序,取前 6。点行跳成员详情。

**项目榜**:**仅累计「真项目」**会话,按 `(gitUser, cwd)` 聚合,rawTotal 降序前 6。项目名取 projects 表 `name`;空时预填完整 cwd(前端仅对纯数字/单字符名回退到末两段)。

### 3.5 代码变动排行

按 `lines`(代码变动行数)降序前 6。

| 列 | 计算 |
|---|---|
| 代码变动行数 | `Σ(added+deleted+modified)` |
| 次对话 | 该成员会话数(含 0-token) |
| **效率** | `代码行 / ((input+output) / 1M)` = 行/M Token;分母 0 → 0 |

### 3.6 会话规模分布

把每个会话按其 rawTotal 规模归桶(**仅 token>0 计入**):

| 桶 | 范围 |
|---|---|
| 0–10K | ≤ 10,000 |
| 10–100K | ≤ 100,000 |
| 100K–1M | ≤ 1,000,000 |
| 1–10M | ≤ 10,000,000 |
| >10M | 更大 |

### 3.7 最近会话表

`/api/sessions` 分页(每页 20)。**过滤 token>0**,按 `lastActive` 降序。

| 列 | 字段 / 计算 |

| 最后活跃 | `lastActive`(`YYYY-MM-DD HH:MM`) |

### 3.8 AI 占比「分母构成」弹窗

### 4.3 禅道工时表(成员详情页底部)

数据 `GET /api/member/:gitUser/worklog`(服务端分页,每页 10)。**台账明细,每条提交记录独立一行,不合并同名任务**。

| 列 | 内容 |
|---|---|
| 日期 | `date`(YYYY-MM-DD) |
| 任务 | `taskName`(可点跳禅道任务页);后缀 `#taskId` |
| 工时 | `hours`(整数 `Nh`,0.5 显示 1 位小数) |
| 工作内容 | `work`(AI 归纳或用户 note,保留换行) |

**数据怎么来的(完整链路)**:

1. 开发者跑 `/report` → skill 侧拆 plan.json 提交禅道 → 成功后逐笔追加 `submitted/<date>.jsonl`;
2. daemon 每次上报全量读 `submitted/*.jsonl`(忽略增量水位),行号即 `subId`,随 worklogs 字段上报;
3. tokenserver 落 worklogs 表,按复合主键 upsert 累积(跨项目/跨天长期保留);
4. 前端按 `date DESC` 排序分页展示。

> 工时数字的口径(时长怎么算、按 note 水位怎么拆 task)见仓库根 `README.md`;worklogs 只存提交结论。
