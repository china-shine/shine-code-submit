## 零、新手快速入门(先读这个)

刚接触这个项目?花 3 分钟搞懂下面几个概念,后面的数据就都好懂了。

### 这个平台是干嘛的?

**AI 效能平台**(tokenserver)是一个**报表看板**,统计一个团队用 **Claude Code**(Anthropic 的 AI 编程助手)的情况:谁在用、用了多少、写了多少代码、花了多少时间。目的是让团队/管理者了解 AI 编程的使用情况,不涉及代码内容,只统计用量数字。

### 3 个必须先懂的概念

**① 会话(session)—— 一次连续的 AI 对话**
你打开 Claude Code 开始跟它聊(写代码、问问题),到结束算一个「会话」。一个会话里可能有很多轮来回(你问一句、它答一句)。页面上「对话次数」统计的就是会话数。

**② Token —— AI 处理的文字量(可以理解成「字数流量」)**
AI 不按「次」或「小时」计费,而是按处理的文字量(token)收费。**1 个 token 大约 = 0.75 个英文单词、或不到 1 个汉字**。一段对话 token 越多,说明内容越长/越复杂、花钱越多。token 分四种:
- **输入(input)**:你发给 AI 的内容(你的问题 + 历史上下文)
- **输出(output)**:AI 回给你的内容
- **缓存写入(cacheCreation)**:AI 把重复内容存起来,下次不用重算(第一次存)
- **缓存读取(cacheRead)**:复用之前存好的内容(命中缓存,比重新算便宜)

> 💡 为什么要分这四种?因为 Anthropic 的计费规则:**缓存读取最便宜、缓存写入稍贵、输入正常价、输出最贵**。所以光看一个总数不够,要看构成。页面上「总 Token」= 这四个加起来。

**③ 活跃时长(activeMs)—— 跟 AI 交互的时长(⚠️ 估算值,不是真实工时)**
平台会估算你「跟 AI 互动了多久」。**注意这不是真实工时**——它看不见你离开 AI 自己写代码、查资料的时间。详见「通用口径 3」。

### 数据怎么来的?(你不用做任何操作)

```
你在电脑上用 Claude Code 写代码
      ↓  (Claude Code 自动把每次对话明细记录到本地文件)
后台小程序(daemon)读取这些记录,统计 token / 时长 / 代码行
      ↓  (默认每 10 分钟自动上报一次,可在设置里改 reportIntervalMin)
AI 效能平台 收数据、存库、画成图表
      ↓
你在浏览器里看到的这个 dashboard
```

只要团队装了 shine-worklog,数据全自动采集上报,**不需要手动填报**。

## 一、数据从哪来

```
Claude Code transcript(.jsonl)
   │  shine-worklog daemon 扫描(逐行解析/校验/去重,口径对齐 ccusage)
   ▼
daemon 定时上报(默认 10 分钟)→ POST /api/report(gzip + 增量水位)
   │  tokenserver saveReport 落库
   ▼
tokenserver SQLite:sessions / projects / git_changes / worklogs 四表
   │  前端请求时二次聚合
   ▼
Dashboard(/api/stats · /api/sessions · /api/member · /api/denominator-breakdown · /api/member/:X/worklog)
```

**上报机制(daemon → tokenserver)**:

- **上报身份 = `git config user.name`**(读全局配置,一台机器所有项目都归该用户名下)。采集不到(未配 user.name,如部分 CI/容器/新机)时**跳过本次上报**,不以「未知用户」上传。多台机器同名 user.name 在平台上合并为同一成员、数据累积(所以平台总量可能大于任何单机 dashboard)。
- **gzip 压缩**:POST 时带 `content-encoding: gzip`,tokenserver 按 header 解压(兼容不压缩的老上报)。
- **增量水位**:`settings.json` 持久化 `lastReportAt`,每次只发 `last_activity >= 水位` 的 session;成功后推进水位,失败不推进(下次重发同批不丢);重启不重置。
- **24h 全量校准**:每满 24h(或 daemon 升级后)强制 `since=0` 全量重报一次,防 tokenserver 数据丢/重置后 daemon 不自愈;`git_changes` 按 hash 幂等 upsert(aiAdded/aiDeleted 取 MAX),重报不重计。
- **禅道工时(worklogs)忽略增量水位,每次全量上报**(daemon 读本地 `plan.json` 的 resolved 条目),tokenserver 按复合主键 upsert 累积。

- **sessions 表**(每行 = 一个会话):`sessionId`(主键)、`gitUser`、`cwd`、`lastActive`(最后活跃,毫秒时间戳)、`input`/`output`/`cacheCreation`/`cacheRead`(token 四字段)、`added`/`deleted`/`modified`(代码行三字段)、`activeMs`(活跃时长)、`title`、`updatedAt`。
- **projects 表**(每行 = 一个用户×项目):主键 `(gitUser, cwd)`,`name`、`gitRemote`、`lastActive`、`version`(该成员最新上报的 daemon 版本,成员列表「上报版本」列)。
- **git_changes 表**(每行 = 一个 git commit):主键 `hash`(commit SHA,幂等去重),`gitUser`、`cwd`、`ts`(提交时间)、`added`/`deleted`(该 commit 代码变化行)、`aiAdded`/`aiDeleted`(其中行级匹配命中 AI 操作的行数)。来自 daemon 上报的 `ReportProject.gitCommits`,`hash` 相同的全量重扫不重计(aiAdded/aiDeleted 取 MAX)。是「AI 代码占比」的分母/分子来源。
- **worklogs 表**(每行 = 一条禅道工时提交记录):主键 `(gitUser, date, sessionId, taskId)`(taskId 空兜底为 0,防 SQLite NULL 互异导致重复),`repo`/`branch`/`start`/`end`/`minutes`/`hours`/`taskName`/`projectId`/`projectName`/`work`(工作内容)/`status`/`zentaoUrl`。来自 daemon 每次上报全量读本地 `plan.json` 的 `status=resolved` 条目(忽略增量水位)。是成员详情「禅道工时」表的数据源。
- **去重**:同一 `sessionId` 重复上报时,仅当新数据 `lastActive ≥ 旧` 或 `cwd` 变了才覆盖(幂等);git_changes 按 `hash` 幂等(相同 commit 不重计);worklogs 按复合主键 upsert 累积(跨项目/跨天长期保留)。

聚合/分页接口(路由见 `src/server.ts`):
| 接口 | 作用 | 后端函数 |
|---|---|---|
| `GET /api/stats` | 总览全部聚合 + 成员列表 | `getStats` |
| `GET /api/sessions` | 会话明细分页(总览表 / 成员详情表) | `getSessions` |
| `GET /api/member/:gitUser` | 单成员 KPI + 趋势 | `getMember` |
| `GET /api/denominator-breakdown` | AI 占比分母构成弹窗 | `getDenominatorBreakdown` |
| `GET /api/member/:gitUser/worklog` | 成员禅道工时分页 | `getMemberWorklogs` |

## 二、通用口径(先读这节)

### 1. Token 四字段 与 rawTotal

每个会话有四个 token 字段(来自 transcript `message.usage`,口径与 [ccusage](https://github.com/ccusage/ccusage) 一致):

| 字段 | 含义 |
|---|---|
| `input` | 输入 token |
| `output` | 输出 token |
| `cacheCreation` | 缓存写入(prompt caching 创建) |
| `cacheRead` | 缓存读取 |

- **rawTotal = input + output + cacheCreation + cacheRead**(四字段全量)。**凡页面上写「总 Token」的,都是 rawTotal**。
- **缓存口径 cache = cacheCreation + cacheRead**(趋势图「缓存」视图、饼图「缓存 Token」)。
- **inoutTokens = input + output(不含缓存)** —— 只用作「Token 效率(行/M)」的分母(分子是会话变动行,完整口径见口径 11)。

### 2. 代码行 lines

`added`(新增) / `deleted`(删除) / `modified`(修改) 三字段,来自 daemon 上报。

- **lineTotal = added + deleted + modified**。凡「代码变动行数」都是三者之和。
- 会话表「代码变动」列**分别**显示 `+added -deleted Mmodified`,不合并。

### 3. 对话时长 activeMs

> **估算值,不是真实工时** —— 度量「与 Claude 交互的活跃度」。算法在 daemon 侧(`src/daemon/transcript.ts` 的 `sessionActiveMs`),tokenserver 只接收上报值求和。详见仓库根 [`对话时长统计说明.md`](../对话时长统计说明.md)。

**gap-aware 切 burst 算法**:把会话内所有交互(usage 消息)时间戳升序排列,相邻间隔 **≤ 1 小时**(`GAP_MS`)的归同一段 burst,**> 1 小时则截断**(视为用户离开)。每段 burst 时长 = `(首条 → 末条跨度) + 10 分钟 buffer`(`BUFFER_MS`,补读回复/思考/测试),多段 burst 求和。

**计算示例**:

| 时间戳 | 算法 | 结果 |
|---|---|---|
| `[10:00, 10:05, 10:12]`(间隔都 <1h,同一段 burst) | 跨度 12min + 10min buffer | **22min** |
| `[09:00]`(单条,单点 burst) | 0 + 10min buffer | **10min**(下限) |
| `[09:00, 12:00]`(间隔 3h >1h,断成两段) | (10min) + (10min) | **20min**(中间 3h 不计) |

**关键性质**:
- 相邻交互间隔 **≤ 1h 计入**、**> 1h 截断不算**。
- 每段 burst 末尾无条件 +10min,任何进报表的会话 `activeMs` **下限 10min**(一句 30 秒问答也算 10min)。
- **自己写代码/查资料只要 < 1h 回到 Claude,这段时间会被算进去**;只有离开 ≥ 1h 才丢弃 → 所以它**不是真实工时**,「适合看交互密度,不适合当人工工时报出去」。

所有「对话时长」= 范围内各会话 `activeMs` 直接求和,格式 `0m`(为 0)/ `<1m` / `Xm` / `Xh`(整点)/ `Xh Ym`。老版本 daemon 可能缺失该字段(显示 0)。

### 4. 日期范围(闭区间,按 lastActive)

前端传 `start` / `end`(YYYY-MM-DD),后端 `parseDateRange`(`src/server.ts`):

- **from** = 开始日 `00:00:00.000`(本地时区);留空 = `0`(不限起始)。
- **to** = 结束日 `23:59:59.999`(即次日 0 点 − 1ms);留空 = `Number.MAX_SAFE_INTEGER`(不限结束)。
- 过滤条件 `WHERE lastActive >= from AND lastActive <= to`,**闭区间**,会话按**最后活跃时间**归属(不是开始时间);git_changes 同用这对 from/to,但按 **commit 时间 ts** 过滤(AI 占比的日期口径 = 提交日,不是会话活跃日)。
- **首次打开页面默认最近 30 天**(开始 = 今天 − 30 天,结束 = 今天);点「重置」才回到全量范围。

> 「重置」按钮:开始 = 全量最早记录(`dataMin`)、结束 = 全量最新记录(`dataMax`),即范围 = 全部数据。
> 「开始日期 ≤ 结束日期」:日历里晚于结束日的、早于开始日的日期会被禁选。

### 5. 粒度 granularity(只影响趋势图)

趋势图可按 `day` / `week` / `month` 聚合(`bucketOf`,`src/store.ts`):

- **day**:日历日,标签 `MM-DD`
- **week**:周一起算的自然周
- **month**:自然月,标签 `YYYY-MM`

> 当前 UI 固定按「日」聚合。KPI 卡的 sparkline 始终按「日」,不受粒度影响。

### 6. 成员 / 项目过滤

- **成员筛选**:URL `members=用户A,用户B`,SQL `gitUser IN (...)`,影响聚合数据(stats)和会话表(/api/sessions)。
- **`allMembers`**(成员下拉选项)= 全表 `SELECT DISTINCT gitUser`,**不受任何过滤影响**。
- **`activeMin/activeMax`** = 当前过滤后数据的 lastActive 范围(顶部「范围徽章」用)。
- **`dataMin/dataMax`** = 全表(无过滤)的 lastActive 范围(重置按钮用)。

### 7. 「真项目」判定(`isRealProjectCwd`)

项目榜、活跃项目数只统计「真项目」,排除盘根/家目录/桌面等。按 cwd 原值(统一 `/`)拆段判定:

| 情况 | 判定 |
|---|---|
| 空 / 段数 ≤ 1(如 `C:`) | ❌ 非真项目 |
| 段数 3 且第 2 段 = `users`(如 `C:/Users/xxx`) | ❌ 家目录 |
| 段数 4 且 = `users/.../{desktop,documents,downloads}` | ❌ 桌面/文档/下载 |
| 其他 | ✅ 真项目 |

> token 总量、对话次数、代码行、成员榜等**不依赖**真项目判定,用全部会话。

### 8. ⚠️ 0-token 会话的口径差异(务必注意)

有些会话四字段 token 全为 0(如纯读取、出错)。它们在不同地方口径不同:

| 是否计入 0-token 会话 | 涉及数据 |
|---|---|
| **计入**(不过滤) | KPI「对话次数」、**KPI「活跃项目」**、对话时长、代码行、总 Token、趋势、饼图、成员榜、**项目榜**、成员「对话次数」 |
| **不计入**(过滤 `token>0`) | 会话规模分布、最近会话表(总览 / 成员详情)的 `total` 与列表行 |

**因此**:KPI「对话次数」 ≥ 最近会话表的总条数(当存在 0-token 会话时)。这是正常的,不是 bug。

### 9. AI 代码占比(只统计有 transcript 覆盖的 commit)

「AI 代码占比」= AI 代码行 / 代码变化行,**仅统计有 transcript 覆盖的 commit**(`aiAdded > 0`),用于看「AI 在可统计代码里的占比」。公式与分子分母口径:

```
AI 代码占比 = Σ(aiAdded + aiDeleted) / Σ(added + deleted)     (cap 100%,分母 0 → N/A)
```

| | 口径 | 关键特性 |
|---|---|---|
| **分母** | **commit 代码变化行** = 该范围所有有覆盖 commit 的 `added + deleted` 之和,来自 `git_changes` 表(`aiAdded > 0` 的记录),daemon 用 `git log -p --unified=0` 采 | **结果量**:git 净变化,反复编辑被折叠;**是 commit 里全部变化行**,包括 AI 没碰过的(见下方「分母里注定不含分子的部分」) |
| **分子** | **其中能行级匹配上 AI 操作的行** = 同一批 commit 行中,内容出现在 AI 编辑操作记录里的行数(`aiAdded`/`aiDeleted`) | **分子 ⊆ 分母**(分子是分母逐行匹配命中的子集,天然 ≤ 分母);与分母对称——AI 删除的行(重构删旧代码)同样计入 |

**怎么判定一行是「AI 写的」——认行不认 commit,四条规则**(daemon `src/daemon/lines.ts` `getProjectAILines` + `aggregate.ts` 行级匹配):

1. **只认 4 个编辑工具**:Edit / Write / MultiEdit / NotebookEdit 的 PostToolUse 操作算 AI 代码操作;**Bash/Grep/Read 等不算**——AI 跑 `npm install`/`npm create vite`/`build` 产生的代码不计入分子;
2. **逐字精确匹配**:commit 的 added/deleted 行内容(连缩进空格)去 AI 操作行集合 `set.has()` 查,**宁漏不错**——被格式化改过一个空格就不匹配;
3. **累积匹配**:AI 操作行集合跨会话、跨多次编辑累积(中间版本都算),手动 commit 的 AI 代码也能识别(不靠 `Co-Authored-By` trailer);
4. **认行不认 commit**:不看 commit 作者和 message,只看行的内容来源。

**分母里注定不含分子的部分**(占比低于直觉的正常来源):`package-lock.json` 等安装产物、`create-vite`/脚手架模板、构建产物(`ui-assets.ts` 等)、格式化输出——这些计入分母但 AI 没「逐行写过」。**实测(2026-08-14 patientMsgService 初始提交)**:全部分母占比 42%,剔除 package-lock 后 82.8%,再剔除脚手架后 **98.6%**——AI 亲笔代码几乎全命中,低占比是生成物稀释所致,初始提交场景最极端。

- **无 transcript 覆盖的 commit(`aiAdded = 0`:早期版本前 / 别机器未装采集)不计入分母**——它们无法判定 AI 占比,计入只会稀释拉低数字,故排除。
- **可选 host 白名单(配置文件)**:`DATA_DIR/config.json` 的 `aiStatsHosts`(数组,如 `["8.130.168.121"]`),配置后只统计 `gitRemote` 命中指定服务器 host 的 commit(公司 git 仓库),JOIN `projects` 按 `gitRemote LIKE` 过滤,排除 localhost/个人/无 remote(NULL)。**空数组或不配 = 不过滤(全部,向后兼容)**。改后重启 tokenserver 生效。

> **旧口径(含全部分母)已弃用**:曾把无覆盖 commit 也算进分母,整体占比被稀释偏低(如全分母 44% vs 有覆盖 61%)。新口径只看「能统计的部分」,更接近真实 AI 代码比例。dashboard AI 占比卡可点「分母」按钮看各项目拆分。
> 实现见 `tokenserver/src/store.ts` `getStats`/`getMember` 的 git rollup(`if (g.aiAdded <= 0) continue`)、`getDenominatorBreakdown`(`WHERE aiAdded > 0`);daemon 侧 aiAdded 计算见 `src/daemon/aggregate.ts`、`lines.ts`。

### 10. ⚠️ 两套「代码行」口径:会话行(过程量)vs commit 行(结果量)

页面上有**两个都叫「代码行」的数字,口径完全不同**,不要互相印证:

| | 「代码变动行数」(KPI 卡 / 成员列表 / 会话表 / Token 效率分子) | 「AI 代码占比」的分母(KPI 卡副标「共 Y 行」) |
|---|---|---|
| **数据源** | transcript 里 AI 工具操作(Edit/Write/MultiEdit/NotebookEdit)的 diff(`structuredPatch`),**不依赖 git** | `git log -p`(已提交的 commit),**必须 commit 才有** |
| **算什么** | 每次工具操作的 +/- 行**全部累积**(中间版本反复计) | commit 的 added+deleted,**git 净变化**(中间反复编辑被折叠) |
| **语义** | 「AI 这场对话动了多少次代码」(过程量,偏大) | 「最终提交改了多少」(结果量,偏小) |
| **代码位置** | daemon `src/daemon/lines.ts` → `getSessionLines` | daemon `src/daemon/git.ts` → `getCommitsInRange` |

实测(2026-08-13 livesetting 项目):会话行 **2280** vs commit 分母 **684**,差 3.3 倍——正常,不是 bug。差异来源:① **反复编辑被 git 折叠**(主因,AI 改 N 次会话列表算 N 次,commit 只算净差);② **会话行是该会话整个生命期的累积**(可能跨天),commit 分母严格按日期窗口;③ **未提交的编辑**只进会话行;④ 反向小缺口:**构建产物**(`bun install` 的 lock、`build:ui` 的 ui-assets.ts 等 Bash 生成物)进 commit 分母但不在 Edit/Write 记录里(→ 进分母不进分子,是「分子 < 分母」的主要原因)。

**推论**:不 commit 的日子里,**Token 效率**(分子=会话行)照常出数,**AI 代码占比**(分母=commit 行)显示 N/A——两者不同空属正常。

### 11. Token 效率(行/M)——分子分母口径

出现在:成员列表「效率 (行/M)」列、成员详情「Token 效率」KPI、总览「代码变动排行」的「行/M Token」。公式:

```
Token 效率 = 代码变动行数 / ((input + output) / 1,000,000)
```

| | 口径 | 关键特性 |
|---|---|---|
| **分子** | **会话代码变动行** = `Σ(added + deleted + modified)`,来自 AI 编辑工具(Edit/Write/MultiEdit/NotebookEdit)每次操作的 diff,**中间版本全部累积**(同段代码改 5 次算 5 次的量) | 过程量。**不是文件实际行数(LOC)**——5000 行的文件只改 3 行,分子只算 3 行;新建 300 行文件分子 ≈ 300。**也不是 commit 净变化**(反复编辑不被折叠)。衡量「AI 挪动了多少行代码」,不反映代码库规模 |
| **分母** | **inoutTokens = `input + output`,不含缓存**(cacheCreation/cacheRead 剔除) | rawTotal 里缓存占比可达 96%+(长会话反复读上下文),但缓存读是廉价复用、不算真实消耗;用 inout 才反映实际处理的文字量。分母为 0(无 inout token)时显示 0 |

**怎么读这个数**:
- 数值高 = 单位 token 产出多(批量生成 / 新建文件型工作天然高);
- **数值低 ≠ 效率退步**:分析代码 / 读源码核验 / 改文档型工作 token 重、变动行少,天然偏低(实测同一天内可从 ~3700 行/M 降到 ~1700 行/M,纯工作类型变化);
- 跨成员对比时注意工作类型差异,写业务代码的和做调研分析的没有可比性。

### 4.3 禅道工时表(成员详情页底部)

| 列 | 内容 |
|---|---|
| 日期 | `date`(YYYY-MM-DD,字符串比较过滤,与顶栏日期范围联动) |
| 任务 | `taskName`(可点,跳禅道任务页 `{zentaoUrl}/index.php?m=task&f=view&taskID={taskId}`);无 taskId 显示纯文本;后缀 `#taskId` |
| 工时 | `hours`(整数显示 `Nh`,小数(0.5)显示 1 位) |
| 工作内容 | `work`(/report 提交时 AI 归纳或用户 note 的一句话,保留换行) |

**数据怎么来的(完整链路)**:

1. 开发者在项目里跑 `/report`(shine-worklog skill),daemon 侧把当天会话的工时按 task 拆成 `plan.json` 条目,提交成功后 `status=resolved`;
2. daemon **每次上报都全量读**所有项目的 `plan.json`(`src/daemon/worklog.ts`,只取 resolved,**忽略增量水位**),随报表 `worklogs` 字段上报;
3. tokenserver 落 `worklogs` 表,按 `(gitUser, date, sessionId, taskId)` 复合主键 upsert 累积(跨项目/跨天长期保留);
4. 前端按 `date DESC, sessionId` 排序分页展示。

> 工时数字的口径(时长怎么算、按 note 水位怎么拆 task)见仓库根 `README.md`「禅道工时闭环」与各 skill 文档;worklogs 表里只存提交结论(几小时、什么任务、什么内容)。

## 五、附录

### 5.1 容易误解的点

1. **「对话次数」vs 会话表条数**:前者含 0-token 会话,后者不含 → 前者 ≥ 后者。
2. **「活跃项目」两种口径**:总览跨用户计数、成员列表/详情单成员 cwd 去重。
3. **Token 效率分子分母都不是直觉口径**:分子是会话变动行(过程量,非 LOC、非 commit 净变化),分母是 inout(不含缓存);低数值常是工作类型使然而非退步,详见口径 11。
4. **对话时长非真实工时**:gap-aware 估算,1h 间隙截断;自己写代码的间隙不计、多会话并行不叠加去重。
5. **团队均值含本人**:不是「除自己外的平均」。
6. **AI 代码占比的分子 ⊆ 分母**:分子是 commit 行逐行匹配 AI 操作命中的子集,永远 ≤ 分母(cap 100% 仅为防御,正常触发不到);占比低于直觉通常是分母含生成物(install 产物/脚手架/构建产物,详见口径 9)。新指标上线时 `git_changes` 为空,占比显示 N/A,需触发各 daemon 全量重报回填。
7. **「代码变动行数」≠「AI 占比分母」**:前者是会话工具操作累积(过程量),后者是 commit 净变化(结果量),实测能差 3 倍以上,详见口径 10。
8. **Token 效率有数但 AI 占比 N/A**:说明当天有会话(过程量有数据)但没 commit(结果量分母为 0)——不是故障,commit 之后 ≤10 分钟占比就会出现。
9. **数据有最多 ~10 分钟延迟**:daemon 定时上报(默认 10 分钟)+ 会话按 lastActive 归日,刚结束的会话/刚推的 commit 可能要等下一轮上报才出现。
